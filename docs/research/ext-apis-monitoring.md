## PART A — Per-Source Technical Dossier

### A1. Grants.gov — Search2 API
- **Endpoint** `[DOC]`: `POST https://api.grants.gov/v1/api/search2` (staging: `https://api.staging.grants.gov/v1/api/search2`)
- **Auth** `[DOC]`, verbatim: *"Authentication and authorization is not required for **search2**"*. API Guide repeats this for `search2` and `fetchOpportunity`. Other Grants.gov REST APIs **do** need a key, obtained by *"open[ing] a ticket with the Help Desk"* — no self-service key issuance.
- **Request body keys** `[DOC]` — from the documented sample plus the echoed `searchParams` object:
  `rows`, `keyword`, `oppNum`, `eligibilities`, `agencies`, `oppStatuses`, `aln`, `fundingCategories`, `fundingInstruments`, `sortBy`, `startRecordNum`, `resultType`, `searchOnly`, `keywordEncoded`.
  Multi-value fields are **pipe-delimited strings**, e.g. `"oppStatuses": "forecasted|posted"`.
- **Response shape** `[DOC]`: `{errorcode, msg, token, data:{searchParams, hitCount, startRecord, oppHits[], oppStatusOptions[], dateRangeOptions[], suggestion, eligibilities[], fundingCategories[], fundingInstruments[], agencies[], accessKey, errorMsgs[]}}`. Each `oppHits[]` element: `id, number, title, agencyCode, agencyName, openDate, closeDate, oppStatus, docType ("synopsis"), alnist[]`. Facet arrays return `{label, value, count}` — usable to enumerate valid codes at runtime.
- **Date filters**: **not documented.** `dateRangeOptions` appears in the *response* envelope but no request-side date parameter is documented. Do not assume one exists.
- **Rate limits**: **not documented.** The API Terms of Service contains only a "Right to Limit" clause `[DOC]`: *"Your use of the API may be subject to certain limitations on access, calls, or use… If Grants.gov reasonably believes that you have attempted to exceed or circumvent these limits, your ability to use the API may be temporarily or permanently blocked."*
- **Mandatory attribution** `[DOC]`, verbatim: *"All services, which utilize or access the API, should display the following notice prominently within the application: 'This product uses the Grants.gov API but is not endorsed or certified by the U.S. Department of Health and Human Services.'"* — **this is a build requirement for NativeForge's UI, not optional.**
- **Documentation defects observed** `[DOC]` (plan around these): one official cURL sample contains an **empty JSON key** — `'{"fundingCategories": "HL", "": "HHS-NIH11", "oppStatuses": "forecasted"}'`; another uses `"oppStatuses": ["closed| archived"]` (array-wrapped pipe string with a stray space); a third uses `"keywords"` where every other example uses `"keyword"`. The API Guide's environment table is captioned *"production and training"* but its rows are labeled Production/Staging.

### A4. Grants.gov — XML Extract (bulk)
- **URL pattern** `[DOC]`: `https://prod-grants-gov-chatbot.s3.amazonaws.com/extracts/GrantsDBExtract<YYYYMMDD>v2.zip`
- **Cadence** `[DOC]`: *"Once a day, the Grants.gov database of grants is exported to an XML file."* Observed timestamps cluster at **~04:39–04:45 AM ET daily**; **78 MB** zipped; **7 days of files listed** on the page (older files are not linked → no long archive).
- `v2` suffix `[DOC]`: *"Files with 'v2' at the end of the filename are the enhanced XML format that **includes grant forecast information**."* The XSD ships **inside the zip**.
- **Full field dictionary is documented** at `https://www.grants.gov/help/xml-extract` `[DOC]`, including all coded value sets. Critically it exposes fields the Search2 API does not: `Estimated Synopsis Post Date`, `Estimated Synopsis Close Date`, `Estimated Award Date`, `Estimated Project Start Date`, `Fiscal Year`, `Archive Date`, `Expected Number of Awards`, `Estimated Total Program Funding`, `Additional Information on Eligibility` (4,000 chars), `Description` (18,000 chars), `Version` (*"'Forecast X' or 'Synopsis X', where 'X' is the version number"*).
- Dates are `MMDDYYYY` `[DOC]` — no timezone, no time component. Parse defensively.

### A8. ★ Simpler.Grants.gov — a real, newer public API (status: live, early development)
This is the most consequential finding versus the assumption that Simpler is vaporware.
- **Base** `[DOC]`: `https://api.simpler.grants.gov`
- **Auth** `[DOC]`: **API key required**, header `X-API-Key: YOUR_API_KEY`. Self-service: sign in to simpler.grants.gov with **Login.gov**, Developers page → "Manage API Keys" → "Create API Key". (No help-desk ticket, unlike legacy Grants.gov keys.)
- **Documented rate limits** `[DOC]`, verbatim: *"by default, **60 requests per minute and 10,000 requests per day per key**. if you need higher throughput for a production integration, please contact us to discuss options."*
- **Key lifecycle trap** `[DOC]`, verbatim: *"Inactive API keys are automatically disabled after **30 days** without use."* → NativeForge must keep a heartbeat call on every provisioned key `[INFER]`.
- **Endpoints** `[DOC]`: `POST /v1/opportunities/search`; `GET /v1/opportunities/{opportunity_id}` (UUID); `POST /v1/extracts`.
- **Search filters** `[DOC]`: `query` (≤100 chars), `query_operator` (`AND`|`OR`), and filter objects `top_level_agency`, `funding_instrument`, `funding_category`, **`applicant_type`**, `opportunity_status` (`forecasted`|`posted`|`closed`|`archived`), `post_date`, `close_date`, `award_floor`, `award_ceiling`, `expected_number_of_awards`, `estimated_total_program_funding`, `assistance_listing_number`, `is_cost_sharing`. Filter grammar: `{"one_of": [...]}` for enums, `{"start_date","end_date"}` for dates, `{"min","max"}` for numerics.
- **Pagination required** `[DOC]`: `{page_offset, page_size (1–100), sort_order:[{order_by, sort_direction}]}`. Sortable: `relevancy, opportunity_id, opportunity_number, opportunity_title, post_date, close_date, agency_code, agency_name, top_level_agency_name, award_floor, award_ceiling`.
- **Hard caps & staleness** `[DOC]`, verbatim: *"Search will only return a maximum of **10,000 opportunities**. Any opportunties past that will be culled for performance"*; and *"Search should return the same data as GET opportunity, except attachments are not included and the data is **cached in search hourly**."* → **search is up to 1 hour stale; attachments require the GET-by-id call.**
- **Extracts** `[DOC]`: `POST /v1/extracts` returns metadata (`extract_metadata_id`, `extract_type`, `file_name`, `file_size`, `download_url`, `created_at`, `updated_at`) for `opportunities_json` / `opportunities_csv`; `download_url` is pre-signed S3 — *"Download URLs may be pre-signed and not require API key."* Official guidance `[DOC]`: *"If you are searching all opportunities then use the extracts endpoint."*
- **`format: "csv"`** is supported on the search endpoint itself `[DOC]`.
- **Write operations explicitly unsupported** `[DOC]`: cannot apply, post opportunities, or create org projects via API.
- **★ GAP — the tribal enum value is not documented.** `applicant_type` values are shown only as examples (`"state_governments"`, `"county_governments"`, `"individuals"`, `"nonprofits"`). **The Simpler enum string corresponding to Grants.gov code `07`/`11` is not stated on any page I read.** It must be recovered from the OpenAPI spec (`https://api.simpler.grants.gov/docs`, which renders client-side — my fetch of `openapi.json` returned empty, and `simpler.grants.gov/api` returned empty). **Action: retrieve the enum from the live Swagger in a browser before writing filter code.** Also note doc inconsistency: examples use both `top_level_agency` and an undocumented `agency` key.
- **Maturity warning** `[DOC]`, verbatim: *"The API is currently in early development. Features are under active development and subject to change."*
- Docs: `https://wiki.simpler.grants.gov/product/api` (also served as Markdown by appending `.md`, and there is an `llms.txt` index — machine-friendly).

### A9. SAM.gov — Assistance Listings (CFDA) Public API
- **Endpoints** `[DOC]`: Production `GET https://api.sam.gov/assistance-listings/v1/search`; Alpha `https://api-alpha.sam.gov/assistance-listings/v1/search`. **GET only**; single search endpoint (no `/{id}` path documented).
- **Auth** `[DOC]`: **API key required**, passed as the **query parameter `api_key`** (no header form documented). Obtained from `https://sam.gov/profile/details` → "Public API Key" field → eye icon → **one-time password emailed** → key revealed. Requires a SAM.gov individual account.
- **★ Rate limits — severe and tiered** `[DOC]`:

| Account | Key | Daily limit |
|---|---|---|
| Non-federal user **with no Role** in SAM.gov | Personal | **10 requests/day** |
| Non-federal user **with a Role** | Personal | 1,000 requests/day |
| Federal user | Personal | 1,000 requests/day |

  **This is the binding constraint on the whole ALN lane.** 10/day is unusable; NativeForge must ensure its SAM.gov account holds a Role to reach 1,000/day, and even then must cache aggressively `[INFER]`.

No last-modified filter is documented.**

| **`ET23020`** | Indian/Native American/Alaska Native Tribal Government (Other than Federally Recognized) | Tribal Government (Other than Federally Recognized) |

### A11. Federal Register API — highest-quality API in the set
- **Base** `[DOC]`: `https://www.federalregister.gov/api/v1`. **Auth** `[DOC]`, verbatim: *"No API keys are needed; all you need is an HTTP client or browser."*
- **Endpoint families** `[DOC]`: published documents (get single by FR document number — *"any Federal Register document published since 1994"*; multi-get; **search**); **public inspection documents** (get, multi-get, search, `current`, by-date — *"available since November 2011"*); **agencies**.
- **`GET /api/v1/documents.json` verified live** `[TESTED]`:
  - `conditions[type][]=NOTICE` → response `{"description":"Documents of type Notice","count":10000,"total_pages":50,…}`
  - `conditions[agencies][]=indian-affairs-bureau` → `{"description":"Documents from Indian Affairs Bureau","count":3313,"total_pages":4,…}` — **agency-slug filtering works and BIA is a valid slug.**
  - `fields[]=document_number` sparse-fieldset projection works.
  - **`per_page` behavior** `[TESTED]`: `per_page=1001` was accepted without error but the response reported `total_pages: 4` against `count: 3313`, i.e. **the server silently caps the page at ~1000 records**. The exact documented maximum is **not documented** on the developer-resources page. `per_page=1` also returned 20 items — small values are floored. Treat `per_page` as advisory, always read `total_pages`.
  - **Deep pagination**: `next_page_url` carries an undocumented **`search_after_cursor`** (base64) `[TESTED]`. This is a cursor-based escape hatch; it is **not** described in the official docs, so do not depend on it contractually.
- **Documented pagination ceiling** `[DOC]`, verbatim: *"Results are paginated; users can customize how many results are returned per page. However, **you can only paginate through the first 2000 results**. If you wish to download more results, use the date range filters."* → **partition every backfill by date range.**
- **Formats** `[DOC]`: JSON **and CSV**; CORS enabled; JSONP via `callback=foo`. Interactive docs at `https://www.federalregister.gov/developers/documentation/api/v1`.
- **Document fields observed live** `[TESTED]` (full record for `2026-17432`): `document_number, citation ("91 FR 55166"), volume, start_page, end_page, page_length, publication_date, type ("Notice"), subtype, title, abstract, action, dates, agencies[{raw_name,name,id,parent_id,slug,json_url}], docket_ids[], dockets[], comment_url, comments_close_on, effective_on, signing_date, correction_of, corrections[], cfr_references[], regulation_id_numbers[], topics[], significant, html_url, body_html_url, full_text_xml_url, raw_text_url, pdf_url (govinfo), mods_url (govinfo), public_inspection_pdf_url, regulations_dot_gov_url, regulations_dot_gov_info{checked_regulationsdotgov_at}, json_url, page_views{count,last_updated}, not_received_for_publication`.
  → `agencies[].parent_id`/`slug` gives a clean **agency/subagency hierarchy**; `docket_ids` + `regulations_dot_gov_url` is the **direct join key into Regulations.gov**; `comments_close_on` is a first-class deadline for consultation tracking; `corrections`/`correction_of` handle amendments.
- **Search parameters**: `conditions[type][]`, `conditions[agencies][]`, `fields[]`, `per_page`, `page` all `[TESTED]`. `conditions[term]` and `conditions[publication_date][…]` are described narratively as *"exposes the full functionality of the FederalRegister.gov advanced search"* `[DOC]` but **I did not individually test them** — confirm parameter spelling against the interactive documentation before coding.
- **Subscriptions/alerts** `[DOC]`: yes, but **human-only and login-gated** — "My Subscriptions" at `/my/subscriptions`, and `robots.txt` disallows `/my/` and `/auth/`. **There is no documented API for creating or reading email alerts.** `[INFER]` NativeForge should build its own alerting on top of the API rather than proxying FR subscriptions.
- **Usage restriction** `[DOC]`, verbatim: *"Republishers of Federal Register material are not permitted to use official NARA or OFR logos or seals."* **No rate limit is stated anywhere.**
- **Legal-status caveat** `[DOC]`: FederalRegister.gov is explicitly *"not an official legal edition… will remain an unofficial informational resource until the Administrative Committee of the Federal Register (ACFR) issues a regulation granting it official legal status."* → for anything a Tribe may rely on legally, link to the govinfo.gov PDF (`pdf_url`) `[INFER]`.
- **Bulk alternative** `[DOC]`: GPO bulk FR XML at `https://www.govinfo.gov/bulkdata/FR`.
- **★ Underused channel** `[INFER]`: the **Public Inspection** endpoints surface documents *before* publication. For a funding-availability notice or a tribal consultation notice, that is a **1–3 business day head start** over everyone polling `documents.json`. Poll `public-inspection-documents/current` every business morning.

### A13. Regulations.gov API
`[DOC]` from `https://open.gsa.gov/api/regulationsgov/`:
- GET API for **documents, comments, and dockets**; POST API for **submitting comments**.
- **API key required**, header **`X-Api-Key`**. `DEMO_KEY` exists but verbatim: *"should only be used for demonstration purposes… It should not be used for anything more than exploring our APIs."*
- **Rate limits** `[DOC]`: *"Please review https://api.data.gov/docs/rate-limits/ for information on rate limits. **Commenting API is restricted to 50 requests per minute with a secondary limit of 500 requests per hour.**"* The default GET numeric limit lives at that api.data.gov page, which **returned an empty body when fetched** → **the GET rate limit is effectively not documented for us; treat as UNKNOWN and pace conservatively.** GSA *"may grant a rate limit increase on the GET keys… Such requests must establish the need."*
- Hard pagination caps documented, with a **`lastModifiedDate` workaround described as "in beta"** for exceeding them `[DOC]`.
- **Comment-API Terms of Participation** bind key holders `[DOC]`: must link the terms of participation and privacy notice in any interface; must certify comments are lawfully gathered from real persons; *"The API key may be disabled if an API key holder is determined to have violated these Terms of Participation."*

- On-site terms pages (`/terms`, `/user-notice`) are **Ember SPAs that served no text** — unread.

### A15. Aggregators to avoid
`[INFER]` — no vendor page was fetched, so this is reasoning, not verification. Avoid third-party grant aggregators (commercial "grant databases," scraped mirrors of Grants.gov) as *upstream sources*: (a) they add latency on top of Grants.gov's own daily extract, so they can only be staler than the authoritative feed; (b) they typically forbid redistribution in their own ToS, creating a licensing exposure NativeForge does not have when pulling `api.grants.gov` directly; (c) their eligibility normalization is opaque, and NativeForge's core value is *correct* tribal-eligibility classification — inheriting someone else's mapping of code `07`/`11`/`99`/`25` destroys the differentiator. The one legitimate exception is **Simpler.Grants.gov**, which is HHS's own product over the same database, not a third party.

## PART C — Monitoring Architecture

### C1. Four lanes, by tier

**Tier 1 — Authoritative spine (API-first, no HTML):**
`Grants.gov daily XML Extract` (system of record for the full opportunity corpus) + `Grants.gov Search2/fetchOpportunity` (intra-day deltas and amendment detail) + `Federal Register API` (notices, consultations, pre-publication) + `SAM.gov Assistance Listings API` (ALN reference and eligibility semantics) + `USAspending API v2` (prior-award intelligence).

Design the spine as **extract-primary, API-secondary** `[INFER]`: reconcile the whole corpus nightly from the 78 MB XML extract — it is the only source carrying `Estimated Synopsis Post Date`, `Fiscal Year`, `Archive Date`, the 18,000-char `Description`, and the 4,000-char `Additional Information on Eligibility` — then use Search2 for hourly deltas and `fetchOpportunity` for per-record amendment forensics. Never make the API the corpus of record; it has no documented date filter and no documented rate limit, which is exactly the wrong combination to build a backfill on.

**Tier 2 — Change-detection on server-rendered HTML** (all confirmed statically scrapeable): OJP current-funding (has a `Date Modified` stamp — use it), ED Available Grants table (CFDA embedded in titles), HUD Exchange `/news/` list, DOE Office of Indian Energy table 1, NIH `WeeklyIndexMobile.cfm`, USDA RD program pages, BIA `/news`, EPA grants pages, NSPIRES front table. Store a normalized-content hash per page-region, not per page — agency footers and view-counters change constantly and will generate pure noise `[INFER]`.

**Tier 3 — Browser automation (last resort, budget it deliberately):** NSF `/funding/opportunities`, NIH Guide search UI, DOE "Other Funding and Opportunities" table, HUD Exchange facet layer, NSPIRES `.do` session search, `sam.gov/data-services`. **Do not run browser automation against hud.gov under an AI-crawler UA string** (robots names ClaudeBot/GPTBot et al. with `Disallow: /`).

**Tier 4 — Email ingest:** DOE Office of Indian Energy **monthly** newsletter (the single most tribal-specific channel), OJP Funding News **weekly** (`topic_id=USDOJOJP_COMMS_25`), NIH weekly TOC listserv, HUD Exchange mailing list, EPA grants listserv (Mailchimp, "periodic"), USDA RD GovDelivery, ED GovDelivery, Grants.gov S2S listservs (breaking-change notice). Provision a dedicated ingest mailbox with per-source plus-addressing so the parser knows the source before parsing `[INFER]`. **Then try to skip email entirely** where GovDelivery archives are public: `content.govdelivery.com/accounts/{ACCT}/bulletins/{id}` is a stable, scrapeable, non-subscribed feed (proven for `USDOEIE`) — probe `USDOJOJP_COMMS`, `USDARD`, `USDE`.

**PDF text extraction lane:** Grants.gov `synopsisAttachmentFolders[].synopsisAttachments[]` (`folderType: "Full Announcement"`), NSPIRES solicitation documents, DOJ solicitations linking to `justice.gov/.../dl?inline`, `ie-exchange.energy.gov` packages, Federal Register `pdf_url` (govinfo) when the legal text matters. **This lane is where tribal eligibility is actually adjudicated** — code `25`/`99` opportunities and `ET12010` Assistance Listings push the real answer into the NOFO body `[INFER]`.

### C3. Deduplication key design

Federal grant data has **no single global identifier**, so use a layered scheme `[INFER]`, built on documented fields:

- **L1 — Opportunity identity (Grants.gov universe).** Primary: `opportunityNumber` (40 chars `[DOC]`) **normalized** (uppercase, strip whitespace/hyphens) — this is the human-facing, cross-source-quotable key. Surrogate: numeric `opportunityId` — stable and the required input to `fetchOpportunity`, but **not** what agencies publish, so store both. **Never key on `title`** (255 chars, freely edited).
  - **Composite required, not optional:** `(opportunityNumber, docType)` where `docType ∈ {forecast, synopsis}` `[DOC]`. **A forecast and its resulting synopsis share the opportunity number.** Collapsing them destroys the forecasted→posted transition you need to detect.
- **L2 — Version identity.** `(opportunityId, docType, revision)` using `revision` from `fetchOpportunity`, cross-checked against the extract's `Version` field (*"'Forecast X' or 'Synopsis X'"* `[DOC]`). A change in `revision` = a new immutable version row; never update in place.
- **L3 — Cross-source join keys.**
  - **ALN** `NN.XXX` `[DOC]` — joins Grants.gov ↔ SAM.gov Assistance Listings (`assistanceListingId`) ↔ USAspending (`program_numbers`) ↔ ED (parsed from program titles). **A single opportunity can carry multiple ALNs** (`alnist[]`, `alns[]`) → many-to-many table, never a scalar column.
  - **Federal Register document number** (e.g. `2026-17432`) — globally unique, immutable, and the natural key for the notice lane. Prefer it over `citation` (`91 FR 55166`), which is page-based and can collide with corrections. Handle `correction_of`/`corrections[]` as a version chain, not as new documents.
  - **Docket ID** (`docket_ids[]` + `regulations_dot_gov_url`) — joins FR ↔ Regulations.gov for consultation tracking.
  - **Agency**: `agencyCode`/`owningAgencyCode` plus `topAgencyCode` `[DOC]` for the agency/subagency split; FR gives the same via `agencies[].slug` + `parent_id`. SAM ALNs use **FPDS codes for Department/Agency and AAC codes for Office** `[DOC]` — a third, non-matching namespace. **Build an explicit agency crosswalk table; do not string-match agency names.**
  - **UEI** for recipient/entity identity (USAspending `recipient`, SAM Entity API).
- **L4 — Fuzzy fallback for sources with no identifier** (BIA news, HUD Exchange, DOE tables, NSPIRES): `SHA-256(normalized_agency + normalized_title + earliest_deadline_date)`, with a secondary near-match pass on normalized title similarity plus deadline-within-3-days. Always resolve to L1 when a Grants.gov opportunity number later appears in the text — agency pages routinely announce an opportunity days before, or instead of, a Grants.gov posting (BIA's Tribal Tourism Cooperative Agreement is the live example).

### C4. Detecting the transitions that matter

**Forecasted → posted** `[INFER]`, using documented fields:
1. From the daily extract, index every record with `docType = forecast`, keying on normalized `opportunityNumber` and retaining `Estimated Synopsis Post Date`, `Estimated Synopsis Close Date`, `Fiscal Year`, `Estimated Award Date`.
2. On each cycle, look for the **same opportunity number appearing with `docType = synopsis`**, or `oppStatus` moving `forecasted → posted` in the Search2 `oppStatusOptions`/`oppHits` payload. **That pairing is the transition event** — emit it as a first-class alert, because a Tribe that saw the forecast has been waiting for exactly this.
3. Also watch `synPostDateInPast` and the presence of a populated `synopsis` block in `fetchOpportunity` `[DOC]`.
4. **Handle the silent-death case:** a forecast whose `Estimated Synopsis Post Date` has passed with no synopsis and no archive. Age it out with an explicit "forecast lapsed — never posted" state rather than leaving it as a live-looking opportunity. This is a common failure mode in naive grant trackers.

**Amendments / modifications** `[INFER]`, in priority order:
1. **`synopsisModifiedFields[]` / `forecastModifiedFields[]` from `fetchOpportunity`** `[DOC]` — a literal list of which fields the agency changed. Nothing else in the federal ecosystem gives you this; make it the primary signal and render it directly to users ("the close date changed," not "something changed").
2. `revision` increment + `synopsisHistCount`/`forecastHistCount` + `opportunityHistoryDetails[]` `[DOC]`.
3. `lastUpdatedDate` vs `createdDate` `[DOC]`; extract field *"Last Updated Date or Created Date — If the opportunity has never been updated, Created Date will appear"* `[DOC]` → **the field is polymorphic; a value there does not prove an update occurred.** Guard for this.
4. `synAttChangeComments[]` and attachment-folder `lastUpdatedDate` `[DOC]` → **a changed NOFO PDF with an unchanged synopsis.** Diff attachment `fileLobSize` + filename to catch re-issued announcements, and re-run PDF extraction when they move.
5. **Materiality classification** `[INFER]`: promote deadline changes, eligibility changes (`applicantTypes` delta), and award-ceiling/floor changes to push notifications; suppress contact-name and description-typo churn. Un-triaged amendment noise is what makes grant alerting unusable.
6. Federal Register side: `corrections[]`/`correction_of` for notice amendments; `comments_close_on` movement for extended consultation windows.

### C5. Two architectural cautions

- **Eligibility must be a graded classification, not a boolean filter** `[INFER]`. `07`/`11`/`08` and `ET23010`/`ET23020`/`ET23030` give high-precision positives, but `99` (Unrestricted), `25` (Others), and `ET12010` (determined at NOFO level) mean the *recall* set requires reading `Additional Information on Eligibility` and the NOFO PDF. A system that filters only on `07|11` will look clean and silently miss a large share of tribally-eligible money — the exact failure NativeForge exists to prevent.
- **Do not let the API become the corpus of record.** Grants.gov Search2 has no documented date filter and no documented rate limit but an explicit right to block; Simpler search caps at 10,000 results and is hourly-stale; SAM.gov allows as few as 10 requests/day. The **daily XML Extract is the only unmetered, complete, fully-documented snapshot in the set** — build reconciliation around it and treat every API as a delta accelerator.
